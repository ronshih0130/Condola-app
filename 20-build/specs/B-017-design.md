## Blocker 3: durable governance and assignment — implemented locally

`20261107020000_b017_custom_role_governance.sql` adds four private org-scoped tables: roles, immutable revisions, retained member assignments (NULL-role tombstones), and immutable request receipts with SHA-256 command digests. Composite foreign keys enforce same-org references. RLS is enabled with all table privileges revoked from PUBLIC/anon/authenticated/service_role. No historical inactive SQL is used as authority.

The five `public.b017_{create,revise,retire,assign,unassign}_role` gateways share one private transaction implementation. `b017_change_member` covers native member transitions. Each rechecks the live session, strictly boolean platform/org flag plus exact allowlist, native Admin governance, effective grant ceiling and resulting usable-Admin/billing-owner state. TS validates static grant shape. Current grant ceilings and target availability are validated only inside the SQL gateway, after authorized receipt lookup/conflict detection. Revision changes invalidate existing assignments until explicit reassignment; retirement also fails closed. Request replays are reauthorized, return their recorded result, and reject changed payload/actor/operation.

Gateway lock order: platform flag SHARE admission → organization → native Admin members in ID order → other members in ID order → roles in ID order → assignments in user-ID order. Locks cover indirect revise/retire effects. Legacy member/invitation writers may already hold a child row; their triggers use NOWAIT to reject an inverted acquisition instead of deadlocking. Member admission touches only the target organization; an OFF organization never locks another ON organization. The caller must retry the complete transaction after a lock conflict.

Local integration evidence covers create/assign/revise/retire/unassign, grant escalation, cross-org references, invalid sessions, immutable history, receipts, billing owner, direct/indirect self-lockout, concurrent last-Admin remove/demote/suspend and waiting self-assignment, real suspend/reactivate/reinvite acceptance and retained tombstones. ## Mode 2 fix round 3 — restriction-only authority (current design)

This section supersedes cross-base grants described in the historical sections. The current package may only restrict a member's native role: **effective permissions = native permissions ∩ current custom grants ∩ mandatory capability floors**. Native role gates and native database RLS remain in force. Cross-base operations (Accountant `props.edit`, Manager `stmt.generate` or `bank.reconcile`) are **DEFERRED / BLOCKED for Claude's tracking**, not positive write acceptance criteria for this package. A reusable role has no target native base at creation: creation/revision must fit the current native Admin actor's effective ceiling; assignment must additionally fit the target member's native matrix. Incompatible assignments fail atomically with `errors.customRoleNativeCeiling`; they never silently gain rights. Current SQL, session permission evaluation and the pure policy evaluator independently intersect native authority.

### One guard and an explicit operation inventory

`b017-entry-permissions.json` maps route handlers, server actions, readers and exported operations to their permission keys. `guardEffectiveSession` reloads authority at the request boundary and callers retain its returned session. `requireEffectivePerm` is the central transactional guard (the old `assertCustomAuthorityOn` name is an alias). `withEffectiveAuthority` finishes each protected transaction with that same check before returning receipts/data or committing writes; read-only snapshots use the central resolver. Explicit post-wait checks precede utility writes, repair expense posting, owner-transfer receipt replay, invoice issuance and vendor sharing. SQL locks the gate, organization, memberships, role revisions/assignments and session until transaction completion; reverse-order lock conflicts fail the whole transaction for retry.

A `null` mapping denies an active custom assignment. It does not deny native/OFF operation or unassigned members. Public login/recovery, consent infrastructure, cron and vendor/portal bearers use their existing distinct authority. Narrow infrastructure exclusions have a reviewed reason and function-body hash in `b017-non-feature-boundaries.json`. The AST regression enumerates every route and use-server export, follows imported calls, checks each named mapping's actual literal key, and checks exported Session transaction functions; new unguarded exports and changed exclusions fail. This is structural coverage, not a claim that static analysis proves arbitrary control flow.

### OFF compatibility

Deployment-unadmitted native requests return before any B017 connection/query. Admitted-but-durable-OFF requests perform the documented gate SELECT; they retain the original native operation SQL, response and copy. Cached custom sessions are refreshed to current native membership before downstream predicates; cached added grants cannot authorize native-Manager bank reads, while cached restrictions no longer suppress legitimate native-Accountant bank reads. A stale custom snapshot needs the resolver query to reload current native authority. The OFF resolver and authorizer join sandbox membership through its live parent, including members invited after sandbox creation without a copied sandbox member row. No remote database has been touched; the migration remains uncommitted and has only been applied to disposable local test databases.
