## Requirements and existing pieces

`20-build/specs/B-013.md`, `B-021.md`, `B-024.md`, `20-build/BLOCKED.md:84`, and `work/B013-source-plan.md` specify one designated currently authorized owner, with a default per owner/org/currency and an optional property override. Strictly **above** the captured threshold needs a decision; equal does not. A new version is required for amount, scope, evidence or designated-owner changes; later threshold edits do not rewrite earlier versions. Decisions are approve/reject/request information for the specific version; silence is never approval. A 24-hour pending reminder is one local event. An admin-only emergency exception requires water/electricity/safety, reason and real photos, audit and immediate owner-notification intent. Vendor rejection preserves the ticket; appointment requires company confirmation; vendor completion awaits company review. Company-reviewed expense is a draft, and a receipt/photo is evidence, not proof of payment or tax qualification. Real delivery and automatic payment are outside this local scope.

The **settings slice** is real source, not an estimate workflow. `supabase/migrations/20261031100220_b013_owner_repair_policy.sql` defines regional/default roots and revisions, override revisions, policy commands, `app.b013_owner_context`, `app.b013_owner_view`, and default change/status/close/finish. `...100221_b013_owner_repair_override.sql` supplies override change/status/close/finish. Their fixed service-role gateways are used by `src/server/repair-owner-policy.ts`, `src/server/repair-owner-override.ts`, `src/app/api/owner-repair-policy/route.ts`, `src/app/api/owner-repair-override/route.ts` and owner pages under `src/app/o/repair-policy/[id]/`; those routes require consent and current session. The `repair_approvals` control combines platform enabled/allowlist and org feature flag. These actions manage settings and request recovery, not decisions or work authorization. `/o/approvals` is still an empty-state page.

Proposed size/count/scale limits are technical proposals requiring PE review, not product limits. No app migration or code in the inspected source mentions these six names outside the handoff; the proposal has no executable estimate, decision, emergency or notification writer and no adopted-work guard. The proposed schema alone cannot enforce correct designation, snapshot authenticity, admin role, immutable underlying photo bytes, prompt-after-24h, or prevent existing writers. A `SECURITY DEFINER` gateway needs narrow service EXECUTE, fixed search path, actual session and actor, selected live/sandbox relation and property/contact/ownership checks; neither client-provided user/role nor a caller-set GUC is proof. Request replays must return their original scoped result and reject changed payload, rather than emit new version or recipient. Head changes, decisions, event intents and applicable business transitions need atomic database-derived proof, not a lookup of any historical approval.

Review control/context and policy/owner admission → ticket → ordered job(s) → version/decision/evidence → expense/intent with actual implicit FK locks, existing photo-limit ticket lock and legacy job-first path; use NOWAIT or a reviewed ordering where a late parent would otherwise block. No global deadlock-free claim follows from this proposed order.

Before any adoption, explicitly define retention/reset for immutable rows and restrictive public parents, including existing guarded demo reset and older-schema absence; no broad production purge or privilege relaxation. Decide how the fixed transaction retains trustworthy provenance through constraint flush and performs a final current-authorization/financial-state check immediately before awaited COMMIT; a deferred trigger forced early is not an unconditional commit-clock guarantee. Preserve existing owner setting values and current legacy semantics where adoption is absent. Neither a settings-only test nor an owner-created synthetic row proves an actual end-to-end producer.
