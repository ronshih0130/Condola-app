# B017 retire an unassigned custom role

**Inactive source candidate for independent review.** The additional fixed command changes one same-live-organization custom role from draft or active to retired. It keeps the row, reserved comparison name, canonical supported keys, creator and creation timestamp. A new request cannot retire that row again. No table or enum alteration is needed. The accepted 01 core already lists role_retire and the 02b audit INSERT policy covers this metadata-only update event.

## Admission, ceiling and concurrency

The proposed function runs in a verified READ COMMITTED transaction. It resolves the pinned live org and actor using the existing effective-context function. Both native Admin and effective team.manage are required. It locks the actual management control, live org, private org state, actor membership and unrevoked/unexpired session. It then resolves current authority again and locks the scoped role and original-command row. The fixed management flag must be an enabled object with a valid allowlist containing the live org; the same live organization must explicitly opt in. The org state must match supported capability version 1 and the exact 17-key manifest. All 18 catalog labels remain recognized; data.export is unsupported in v1.

This fragment requires the original template keys to be contained in the actor's current effective keys, including on replay. It applies the actor ceiling to destructive administration of the template. The bound is independent of any target's native base. The command accepts no keys, actor ID, name, replacement role or classification of the target as unassigned. An empty template still requires both governance predicates. No role can be retired if any matching assignment points to it, including the actor's own assignment or a retained assignment for an inactive/removed member. A NULL-role tombstone is unrelated. No membership, assignment, billing owner, last usable administrator, session or portal rights are changed.

All future role/assignment/import/raw-authority writers must acquire the same live-org and private state locks before changing authority and must reject assigning a retired role on a fresh locked read. The role's FK alone permits references to a retained row and cannot prove that future writer's lifecycle check. Pending raw guards, immutable role/receipt protections, deferred usable-Admin enforcement and worker isolation remain integration prerequisites. Target NOWAIT, lock timeout, deadlock and serialization errors remain failures. A timeout or lost acknowledgement cannot authorize a second write.

## Exact retry

The receipt key remains (org_id, actor_member_id, request_id). The original intent commits a fixed operation/version domain, org, actor membership, request, role, both caller-supplied expected revisions, supported catalog digest and a server-derived 17-bit template mask. Bit zero corresponds to the first element of b017_supported_keys_v1(). The private result contains bounded numeric mask, support digest, role ID and the two original post-operation revisions. It contains no display name, permission text, session credential or bearer. No mask or key list is returned to the caller or included in the audit.

A retry passes current authorization and lock checks before reading the receipt. An exact request reconstructs the historical template ceiling from its original integer mask and current pinned capability digest; it validates the entire result and intent commitment. Changing request content under the same command key yields conflict; malformed or inconsistent historical evidence yields unavailable. An exact authorized retry returns only original metadata, even after unrelated org authority changes. Both recorded result revisions must equal the submitted pre-revisions plus exactly one. A later illegal reference to the retired template makes even a matching replay unavailable. A new request encountering a retired or missing role cannot revive it. Original receipts are append-only by contract; enforcement against other writers is required before any runtime use.

A first success increments the role and authority revisions once, updates lifecycle/actor/timestamp and inserts the metadata audit and receipt in one transaction. The final check verifies the actor/session/org and same effective key set and assignment/template revisions despite the expected org epoch increment. A failure after the first write raises and rolls the transaction back. The trusted adapter must authenticate the actual cookie, pin canonical org/environment, hold and freshly confirm consent, partner and source/session conditions after waits and before verified COMMIT. SQL results are provisional until commit acknowledgement. An uncertain commit calls for bounded same-original-request recovery, never automatic resubmission.

## Deployment boundary

The proposal seals the new signature to its NOLOGIN owner, rejects residual non-owner function ACLs and rejects owner membership/privilege drift. There is no runtime EXECUTE grant, adapter callsite, control registration, org enrollment, role activation, SQL parser result or target execution. Existing source dependencies supply the prospective owner row-lock privileges, RLS policies and metadata audit insert. Their sealed compiler handoff is a separate three-input artifact. Its exact catalog assertions and RESTRICT removal are incompatible with adding a fourth input or eleventh signature in place. A separately reviewed successor would need its own install/down inventory, dependency-bound receipt and exact operator/target approval. The current core cannot prove complete operation-package readiness or worker fencing from its key digest. The supplied command is live-org-only; approved sandbox governance still needs its own compatible composition.

All target vectors are NOT RUN. Separate source review and the eventual real, isolated PostgreSQL target proofs are required.
