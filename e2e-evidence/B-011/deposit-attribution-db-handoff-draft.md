## Existing sources and one proposed durable object

Current `public.payments` records org, lease, gross amount, currency, status, confirmation, optional proof and deposit flag; `(org_id,id)` is the available composite key (`20261018120000_schema.sql:942–974`). `payment_allocations` connects a payment to an invoice, not a particular invoice line (`:980–990`); `invoice_lines` supplies charge types, amounts and optional period (`:858–875`). `public.files` has `(org_id,id)` (`:286–298`); existing `app.handover_attachments` has `(org_id,lease_id,id)` (`20261031100214_b011_handover_records.sql:46–59`). These foreign keys and proof references do not establish live authorization, source identity, retained deposit, lease match, currency match, confirmed/unreversed status or money availability.

The SQL proposes one private append-only `app.b011_deposit_attribution_revisions` table, not a generic accounting system. Each row records an org and original lease, logical root and revision/expected prior, stable payment or operator-canonical external identity, currency, nonnegative gross snapshot and manually evidenced attributed amount, scalar file or same-lease handover attachment, provenance, reason, actor, request UUID, payload hash and timestamp. The first row for a payment is unique per org/payment irrespective of lease; an external root is unique per org/normalized namespace/identity. The chain keeps original source identity, root, org, lease and currency; one successor per prior and consecutive revision numbers retain correction history. Amount zero records a correction or withdrawal. The proposed gross constraint only bounds that row's snapshot, not current funds. Latest effective revision counts once; never sum superseded revisions as extra deposits. The table alone does not implement a current selector, lock protocol or source authority.

An optional scalar `attribution_revision_id` is added to the separately proposed `app.b011_settlement_sources`, with an exact `(org_id,lease_id,id)` FK to this revision. It is an additional reference, not a replacement for the existing source's exact-one payment/handover/file evidence constraint. No data is backfilled. Its FK does not prove that the referenced attribution is current, its payment matches a source-row payment, its currency matches the version or its use is authorized; future gateway checks must establish these relationships. A snapshot is historical evidence, never automatic financial completion.

## Manual amounts, allocations and unknowns

For a 30,000 payment allocated as 30,000 to an invoice with 20,000 rent and 10,000 deposit, an authorized admin/accountant may record an evidenced 10,000 deposit. The invoice allocation is context for the **same** payment, not another 30,000 cash consumption to subtract. Ron's policy does not require classifying every remainder of a payment before recording the supported deposit portion. Check actual source amount and current evidence, and account for **genuinely independently exclusive** uses of the same funds without counting the same invoice allocation or attribution twice. When evidence of identity, amount, currency, retention or exclusive use conflicts or is insufficient, keep the relevant amount UNKNOWN; do not manufacture availability. The SQL's `gross_snapshot_minor` is a human/system snapshot only and cannot settle these cases.

External namespace/identity is an operator assertion supported by evidence and local uniqueness, not bank-wide knowledge. Different labels, namespaces, a payment row and an external document may still describe the same real transfer. Future verification must detect or resolve suspected cross-kind/document duplicates and retain UNKNOWN where the identity cannot be established. Normalization and a unique index alone do not establish economic uniqueness. Do not infer retained deposit from a contract amount, `is_deposit`, payment proof, invoice-paid status or this row alone.
