## Narrow future admission boundary

Codex must design and implement fixed create/replay and reversal gateways, admission guards, application port, executable migration and local proof; PE later owns target validation, security review and separately approved non-Mac application. No generic ledger adoption framework or wider authenticated UPDATE grant is proposed.

- A narrowly scoped header guard admits typed markers only from the dedicated fixed gateway identity. Any reversal of a typed original must be rejected unless it comes from the reviewed fixed reversal gateway, even if a direct caller or either generic reversal overload creates an unmarked header. Preserve valid untyped reversals.
- A child admission guard must likewise prevent direct extra entries under typed parents while permitting legitimate ordinary untyped transactions. For **every** referenced parent, resolve its globally unique ID and require an actually existing, correctly scoped organization and a definite allowed classification. A `NOT EXISTS typed` query is never sufficient: RLS may hide a typed row, and a concurrently uncommitted typed insert may not yet be visible. Missing, invisible, wrong-org or ambiguous parent results must deny without exposing raw existence. An uncommitted parent that is not visible must be denied rather than admitted while its later FK waits. Once visible, typed admission must still be denied. Do not turn this into a blanket lock or privilege requirement on ordinary untyped writers.
- Classification must be trustworthy across RLS and FORCE RLS and must not become a reusable public existence oracle. A tiny privileged classifier may return only the minimum classification after an invoker trigger has separately captured/checked the real caller identity; the exact design, grants and visibility require target review. ## Order of authorization, replay and new work

Every command must validate the current authenticated actor, org, live parent, selected environment, session and feature controls and compare them with the **rendered original `expectedScope`** (user, org, live parent, environment). This is a precondition, not self-authenticating client input. The persisted recovery intent must retain that original scope; stale scope cannot start or replay a different actor/org/environment operation. Current browser source stores scoped request intent in sessionStorage (`src/components/owner-transfers.tsx:12–19`, `src/server/owner-transfer-input.ts:38–51`). Old unscoped recovery cannot be silently accepted or reinterpreted; hosted privacy/recovery treatment is a separate unresolved product decision. Define sensitive payload minimization, retention/TTL and cleanup without inventing a settled policy. OFF recovery remains outside the current contract.

After current scope authorization and the same org transaction lock, resolve the exact request UUID **before** new-operation checks. For an existing committed request, compare original actor and original intent against the stored marked header and exact two validated legs, using their stored currency, `b014:v1:scale=N`, date, property, owner and amount. An exact original retry returns the same committed result even if the owner roster, currency precision or month-close state changed later; a different payload or actor rejects. Do not replace stored scale or owner with current settings when checking a past request. Valid current session/scope/feature authorization remains necessary; no cross-scope historical disclosure follows.

For a genuinely new create only, check current effective property-owner relationship, configured currency/scale, complete intent, and open posting period, then atomically insert the marked header and exactly two prescribed legs. A new reversal validates the original stored marked header and exact two stored legs, uses their amount/currency/scale, a separately supplied valid open reversal date and reason, and inserts exact opposite legs linked to the original. Do not use an unbounded insert-select of all present entries. For an already committed reversal UUID, exact stored-payload replay occurs before a newly closed-period or changed-roster check. One-reversal uniqueness is a backstop, not authority. Verify final current session/relationship and precise source/authority change guarantees under actual concurrency; last application read alone cannot prove absence of a later uncooperative mutation.

## Month-close, rollout and owner reads

A narrowly scoped `BEFORE INSERT` on `month_closes` can take the same transaction advisory lock for legacy as well as current closes; typed gateways must acquire the identical key and check the posting period after acquiring it. Preserve normal untyped ledger work. Require fresh post-wait visibility: a preexisting REPEATABLE READ snapshot can miss a newly committed close, so restrict invocation/isolation or prove a serialization/retry design. Test close-first, writer-first, absent close, rollback, old direct close, unrelated org, lock order and actual timestamp/date handling. A close INSERT trigger does not protect privileged UPDATE, DELETE, reopen or maintenance paths; inventory these separately.

Classify existing marked rows at a transactionally meaningful rollout boundary, including all children and reversals. Even an apparently exact pair may have been forged by earlier direct writers; ambiguous provenance must be quarantined, not promoted to trusted history. Address writes between inventory and guard installation. Current TypeScript directly inserts marked headers/entries; installing guards alone will block it. Codex must port the writer and test new/old workers in a controlled OFF sequence before relying on it. Reverting code to the old direct writer with guards installed can deny operations; dropping guards while trusted rows remain can reopen tampering. Neither is a verified rollback until actual target tests, backup/restore and explicit fix-forward/rollback evidence exist.

Keep owner projection separate and disabled until a precise access contract exists. Define the individual recipient, org/environment, current and historical ownership, reassignment and multiple-owner cases, explicit field allowlist and negative privacy tests. Staff access or current ledger RLS does not imply owner access. Do not project free-text transfer references, other owners or bank details by default. A contact ID in a ledger entry is a recorded recipient claim, not proof of a bank transfer.

Existing company-directed payment recipient evidence, full cash/payout cross-period reconciliation, negative-net presentation, immutable corrected report versions and delivery metadata remain separate B-014 work. `statement-calculation.ts:27–55` selects confirmed property payments but does not itself prove who received the money and omits typed payout events in its closing formula; `domain.ts:2357–2364` currently writes zero payouts. Existing notification/delivery data may be reusable, subject to exact report-version/recipient semantics; do not assume a new table. No bank transfer or external message is authorized.
