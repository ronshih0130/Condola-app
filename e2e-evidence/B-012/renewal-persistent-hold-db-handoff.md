## Design and actual baseline

One additive `public.leases.b012_renewal_draft_hold boolean NOT NULL DEFAULT false` stores the marker on the parent itself. Atomic parent and marker creation prevents an independently orphaned hold-table row; deleting a parent also removes its column. This does **not** establish that demo reset, retention, deletion, replication, or all old code are safe. No table permissions or existing RLS are changed. A platform metadata row for `lease_renewal` is proposed only when missing, disabled with an empty allowlist; conflict leaves an existing value untouched. No flag is enabled, and an existing value cannot be assumed disabled.

The `leases` schema in `20261018120000_schema.sql:501–558` has `status`, `esign_status`, `signed_at`, `document_file_id`, `document_sha256`, `previous_lease_id`, creator/time, space and currency. Existing `idempotency_key` is **nullable text**, with an org-scoped partial unique index (`20261027130000_lease_idempotency_key.sql`). Newly held rows must store `b012-renewal-draft:v1:<canonical-lowercaseUUID>:<64-lowercase-hex CREATE-payload SHA-256>` there; the complete original key is immutable while held even when draft terms later change. This is original request identity, not a hash of the current edited terms or financial authority. A narrow proposed partial unique expression index on `(org_id, split_part(idempotency_key, ':', 3))` for held rows rejects reuse of one request UUID with a different hash, parent or creator; the existing full-key index and unheld keys remain unchanged. The SQL validates format but does not prove that a supplied hash matches a canonical payload. A future fixed writer must lock the organization and request UUID, look up the namespaced UUID, and verify original hash, previous parent, organization and creator. An identical original create replay returns the same current draft even after edits; a changed original payload with the same UUID must fail. Canonical serialization, hash computation, authority and replay handling are future work, not implemented or tested here.

The proposed parent trigger accepts a true hold only on a new, identified, linked, unsigned `draft` with `not_sent` e-sign state and no document file or digest. For any update it rejects true/false transitions, and while held preserves org/id/previous link/creator/time/idempotency/space/currency and the unsigned state; other draft terms may be edited. The proposed parent trigger name `zz_b012_guard_held_lease` sorts after the baseline `trg_lease_target_guard` normalizer (`20261018120000_schema.sql:1670–1710`), so its check sees that normalizer’s changes. The actual target catalog and order of every relevant BEFORE trigger must be verified before application; a later normalizer could invalidate this assumption. There is no owner/current-user exemption and no flag-dependent bypass. The previous link's same-org validity is left to the baseline FK. It does not by itself validate comparison, overlap, parent relationship, parties, role, tenant identity, or business-complete terms.

Four proposed child triggers block insert or rebind involving a held lease for `public.esign_cases`, `public.lease_signatures`, `public.lease_signed_pdfs`, and `public.invoices`. These actual tables all carry `lease_id` and `org_id`: see `20261030150900_esign_core.sql:5–13`, `20261018120000_schema.sql:578–602,817–829`, and `20261021140000_basic_leases.sql:29–49`. Parent lookup uses globally unique lease ID independent of the caller-supplied org, so a wrong child org cannot hide a held parent. A missing/null parent is rejected; baseline FKs and RLS govern unrelated invalid relationships. The lookup locks matching parents in ID order. Security-definer ownership and visibility must be verified on target, including forced RLS and least-privilege behavior. No generic payment, ledger or notification writer fences are introduced.

Existing legacy creation uses explicit column lists in `src/server/domain.ts:998` and adds signatures at `:1054–1060`; enhanced e-sign creates cases in `src/server/esign/repo.ts:249`; move-in billing inserts invoices in `src/server/move-in-invoice.ts:72`. These observations do not prove compatibility. `src/server/onboarding-progress.ts:33` uses `SELECT l.*`, and other row types, B-001/B-007/B-008, paper signing, legacy creation and enhanced e-sign require compatibility review. An ordinary new or existing row with the default false hold is intended to preserve normal behavior, subject to testing.

## Required future writer and validation

A future fixed, authenticated writer must create the new unsigned draft, required parties, true marker and durable request identity together in **one transaction**. There must be no standalone unguarded public insert/mark-existing endpoint and no provisional unheld renewal draft later marked held; proposed SQL rejects marking an existing row and release. The writer must validate active session, organization/environment, role, previous lease, parties, complete terms, permitted edits, canonical original CREATE-payload hashing and replay equality, locked org/request-UUID lookup, original parent and creator checks, and current flags. The same original payload retry must return the current draft even after edits; a changed original payload under the same UUID must fail. A true hold can currently be supplied by any role already authorized to insert a lease: the guard prevents activation side effects but does **not** authenticate a renewal creation. Future endpoint authorization and existing insert privileges must be assessed before any exposure. It is not an API or permission grant.

The proposed guard locks parent rows and rejects missing parent IDs before the FK runs, but exact MVCC behavior, concurrent inserts/updates, trigger ownership, statement snapshots, deferrable constraints and old callers require real tests; no race-free guarantee is claimed. With an atomic held parent created first, a child attempting to use it must either observe the hold or fail; test transactions paused before parent commit, child-before-parent, wrong-org child, rebind in both directions, and concurrent parent deletion or term edits. Check READ COMMITTED and any isolation levels used by application. Explicitly prove no previously created case can be rebound to the held parent and no preexisting child reaches held creation through deferred or unusual FK paths.
