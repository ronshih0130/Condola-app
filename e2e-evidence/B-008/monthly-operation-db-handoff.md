## Contract and limits

This is an additive private foundation for one fixed monthly rent operation. Its own completed operations have at most one occurrence per `(org, lease, month_start, rent)` and one completed command per `(org, actor, request_id)`. A command refers to exactly one occurrence of the same organization; an occurrence may have multiple immutable commands, one per completed request key. The immutable receipt records an internally consistent as-of issuance snapshot. It does **not** prevent another authorized existing or future direct writer from inserting, editing, voiding, or deleting public finance data, and does not promise a globally unique rent invoice. Changes concurrent with the snapshot may be invisible to it; later replay must surface them. Reconcile and test ordering against legacy writers; do not claim universal serialization.

The existing source planner `src/server/monthly-rent-operation-plan.ts` uses literal version `monthly-rent-operation-v1`, SHA-256 of its canonical JSON normalized source, and produces `leaseId`, property, payer, currency/config, amountMinor, service period, due date and digest. The writer must use that exact shared planner and canonical byte encoding; no fingerprint on unsupported results. The approved first-period rent/30 daily decision is already resolved and is separate; do not transfer it into this full-month rent-only operation or ask Ron again. No utilities, deposits, fees, move-in issuance, partial period, zero amount, or unsupported lease is included. Full B008 requires separate preview/generation parity and utilities/statement work.

## Proposed objects

* `app.b008_monthly_rent_occurrences`: explicit UUID, durable organization and composite `(org_id, lease_id)` parent references, first-of-month finite four-digit supported range 0001-01 through 9999-11, fixed kind, positive bigint minor amount, referenced ISO currency, exact planner version and 64-lowercase-hex digest, original issuer and invoice/rent-line/ledger-transaction UUIDs, a structurally checked versioned snapshot, and finite creation timestamp. The org/lease/month/kind unique key arbitrates this writer. The `(org_id,id)` key supports the command's composite FK. No cascade is specified. Parent deletion is therefore blocked while receipts exist.
* `app.b008_monthly_rent_commands`: explicit UUID, organization, historical actor UUID, request UUID, fixed intent version and canonical intent digest, occurrence UUID, `result_kind` (`created` or `already_issued`) and finite created time. `(org_id,actor_user_id,request_id)` is unique and its `(org_id,occurrence_id)` FK prevents cross-org binding. A different authorized request for an already-issued month appends its own `already_issued` command bound to that occurrence and intent, without any new occurrence or financial write. The creation command uses `created`; replay of either command returns its stored result and is identified as a replay. The original issuer UUID remains on the occurrence; all actor UUIDs are historical.
* Both tables have RLS enabled, no app policies, and all privileges revoked from PUBLIC, anon, authenticated and service_role. No app/service grant is introduced. The small shared BEFORE UPDATE OR DELETE trigger always raises, including for ordinary owner operations; function execute is revoked from those roles. The trusted owner can disable/bypass triggers or change schema and is not constrained as a hostile actor. TRUNCATE is not protected by this trigger; owner is trusted and no runtime role receives it. Check inherited/default privileges and ownership, not just explicit ACLs.
* The global `monthly_rent_posting` row is inserted as `{"enabled":false,"allowed_org_ids":[]}` without conflict masking; a pre-existing key makes the transaction fail. For new financial creation the future writer must require the existing preview gate AND an independent posting gate: posting global `enabled` exactly JSON true, `allowed_org_ids` a JSON array containing the selected organization UUID string, and the selected organization override `feature_flags.monthly_rent_posting` exactly JSON true. Missing, malformed or false gate data fails closed, including invalid allowlist elements; validate the complete expected shapes. Preview alone cannot enable posting. Current-authorized read-only history recovery remains available when either creation gate is OFF; it performs no command insertion or creation. This proposal does not alter an organization or turn on a flag.

`actor_user_id` and payer identity in the snapshot are historical identifiers, deliberately without user/contact FKs: a receipt must not prevent a user/contact deletion or cascade away its replay key. The durable org and lease references intentionally can block parent deletion, which must be assessed against privacy, retention and account deletion workflows before approval. Minimize snapshot personal data (prefer stable IDs over names); restrict access and do not invent a legal retention period. There is no ordinary runtime purge or automatic reissue, including after void/deletion. Any future lawful retention/deletion mechanism needs separately reviewed requirements and an explicit dedupe/reissue consequence.

The output UUIDs are **historical**, not foreign keys. The frozen minimal `b008-monthly-issuance-v1` envelope requires string keys `version`, `orgId`, `leaseId`, `monthStart` (YYYY-MM-DD), `amountMinor` (canonical decimal integer string), `currency`, `planVersion`, `planDigest`, `issuerUserId`, `invoiceId`, `rentLineId`, and `ledgerTransactionId`; each is bound by the SQL check to its corresponding receipt column. It requires nonempty objects `source`, `invoice`, `rentLine`, `ledgerTransaction`, and a nonempty array `ledgerEntries`. The check uses `IS TRUE` so missing/null/type-mismatched fields fail. Nested contents and actual finance relationships are not independently proven by DDL. Trusted server code must validate all nested types and contents against actual outputs before insert. No raw request body or secrets belong in the snapshot. The versioned snapshot must include normalized source/eligibility evidence used for the digest, selected environment, organization/lease/property/payer IDs, amount/currency/config, inclusive period and exclusive end, due date, invoice identifiers/number/status and relevant fields, exact created rent-line identifiers/amount/currency/service period, ledger transaction and every created ledger-entry identifier/account/signed amount/currency and links, validation outcome and issuance time. Avoid unnecessary names. On authorized replay, return the original receipt with separately loaded current source and output state, explicitly `unchanged`, `changed`, `missing`, or `void` where applicable; do not silently regenerate or call the original snapshot current. Current state is itself as of its read and may subsequently change.

## Future fixed writer protocol (not implemented)

The sole proposed entry is an internal server TypeScript module `writeMonthlyRent(session, {leaseId, month, requestId, expectedDigest})`; no generic completion RPC, caller-supplied amount, payer, output IDs, privileged SQL, or arbitrary financial pointers. Resolve the actual session, live/sandbox selected org, consent and membership using existing authority helpers. Writer authorization must check the real current database membership role Admin or Accountant (not a view prop); Manager may preview only. Recheck session and membership for every request. For new financial creation, recheck both the preview gate and independent posting gate within the transaction, with appropriate locks and a bounded timeout; fail closed on unknown authority, malformed flags or source state. Current-authorized read-only recovery of existing history must work with either gate OFF and makes no writes. A new `already_issued` command is a write and requires the full creation gates as well as current authorization; OFF history recovery never appends one.

1. Start one transaction and acquire `LOCK TABLE public.platform_settings IN SHARE MODE` before request keys or parent locks. This conflicts with the disposable reset's SHARE ROW EXCLUSIVE admission. Acquire a transaction-scoped request advisory lock keyed by unambiguous domain-separated `(org, actor, requestId)`; define encoding/hash and collision behavior in implementation. Lock the lease domain in the same documented order as compatible existing writers, considering `FOR NO KEY UPDATE` versus `FOR UPDATE`, FK key-share edges and parent order. Read and lock flag/auth sources consistently. Avoid lock upgrades; use bounded timeout and handle deadlock/serialization retries. This ordering is a requirement to investigate, not a claim of deadlock freedom.
2. Inspect the completed command before recalculation. Same key and same canonical intent returns the recorded result marked replay after current authorization and separately reports current drift/missing/void, even when gates are OFF; same key with different intent rejects. A distinct request encountering an existing occurrence may record `already_issued` only after full gate and authorization checks, without creating finance rows; it binds its own canonical intent and occurrence atomically. If gates are OFF, only authorized read-only history can be returned and no new command is recorded. Canonical intent must unambiguously bind version, selected org/environment, actor, leaseId, normalized month and expectedDigest with specified UTF-8 encoding and SHA-256; never trust client-created digest except as the expected preview value. Exact version/canonical test vectors must be frozen in the writer review.
3. For a new request, read every planner source from one consistent database snapshot, including all relevant rent lines and missing/NULL history, currency metadata, property, lease, parties and unarchived contact. Re-run the shared pure plan and compare exact `expectedDigest`; refuse unsupported, stale, ambiguous, capped or changed data. Specify isolation and snapshot acquisition precisely and test waiting-lock snapshot freshness; restart the **whole** transaction where required. The recorded snapshot is consistent as of that snapshot, not proof that independently authorized direct writers cannot change sources later or concurrently.
4. Under the authenticated database role, derive and create the invoice, single rent line and balanced ledger transaction/entries in that same transaction, using actual `RETURNING` IDs and the existing finance semantics. Validate actual org, lease, property, payer, period, currency, amount, links, line count, source and ledger balancing, not just expected input. Briefly switch to the specifically verified owner role only to insert the complete occurrence and then complete command; restore authenticated role immediately, including exception-safe handling. Feasibility of that precise role-switch and session authority model is a blocking PE validation item, not a new Ron product decision or an assumed capability. Prior staged old-capture metadata reported login owner=true and current_can_set_auth=true; it does not establish ownership or privileges on these new data structures. No general-purpose privileged client API or issuing RPC is introduced. Entire transaction rolls back on any fault or unique/FK conflict. Recognized conflicts get bounded whole-transaction retry/readback; never swallow an unexplained constraint error.
5. On uncertain commit, open a fresh authorized transaction, recover by the same org/actor/request key and canonical intent, and return recorded result if present. If absent, report unresolved or bounded-retry the same request, never manufacture success or use a new key. Concurrent different request IDs for the same own lease/month race at the unique occurrence constraint: loser fully rolls back all attempted finance writes, then in a fresh authorized and gated transaction records its own complete `already_issued` command against the existing occurrence, with request-key lock and unique constraint protecting intent binding. If authorization or gates no longer permit that write, return only authorized read-only history without claiming the new request completed. A retry rechecks the request key and intent. Avoid returning another actor's sensitive receipt without explicit current access checks.
