## Contract and scope

Add one `payment_result_enabled boolean NOT NULL DEFAULT true` column to the existing private `(org_id,user_id)` preference row. Separate fixed get and set functions derive the user from `auth.uid()`; callers pass only the selected organization, live parent, environment, session, lease, and for set a boolean. The authorization and NOWAIT row-lock predicates follow the existing due preference: selected org/live-parent/environment consistency, current unrevoked and unexpired session, unarchived contact linked to the user and primary/co-tenant lease party. Like existing code, service-role execution is limited to a server-controlled authenticated subject; it is not authority to accept an actor from a client. The setter takes `platform_settings` SHARE NOWAIT after initial authorization and before parent and preference row locks, matching the existing due setter's admission order against demo reset; this coordinates reset and is neither a rollout gate nor a new general writer fence. The read-only getter does not take that writer admission lock. The setter rechecks session expiry after the preference-row wait, updates only payment preference and `updated_at`, and atomically writes a redacted old/new boolean audit record only for a change. A failure rolls back both. The row's setting applies across the user's eligible leases in the same org. Null setter input is rejected.

Absent preference means enabled. Adding a constant true default gives existing rows the same payment default. The insert uses the existing default for `due_enabled` and `ON CONFLICT DO NOTHING`; an existing due value, including false, is never overwritten. Existing due getter, setter and capture semantics are unchanged. Source reset clears this private table with other demo rows; therefore the new value is also reset along with it. Verify intended demo versus live reset boundaries before adoption.

The functions intentionally do not couple the personal setting to the rent or payment feature flags: the future server UI/capture must separately enforce its own payment feature gate and availability, and use an appropriately locked/revalidated preference at the point of capture. Neither this draft nor the current setting creates a claim, ensures opt-out against in-flight capture, dispatches an Email, or establishes provider receipt. Captured is not delivered. Existing B028 claims already contain an Email channel, state/token/attempt, captured/failed metadata and recipient/event uniqueness; future payment capture needs its own fixed implementation and concurrency contract. Existing-schema actual in-app center work is separate and is not blocked by this proposal.
