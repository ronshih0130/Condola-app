## Boundary and contract

- Admin staff on the current selected live company may read or propose changes to existing `organizations.legal_name` and `tax_id`, and the private extension's `city`, `district`, and `street`. Text is self-reported: no checksum, registry, verified identity or legal-status claim. The exact accepted country and jurisdiction are `TW` / `TW`; missing, inconsistent or unsupported values fail closed. Existing audiences for base company columns are unchanged.
- The extension has one row per company; absence means empty address/version zero. The exact schema marker is `company-tw-text-v1`. A changed address increments version, including clearing it; no migration backfill occurs. Ordinary roles, including service_role, have no direct table grant; RLS is enabled but not FORCE. The table and SECURITY DEFINER function must be owned by the same actual trusted non-app owner as the canonical B003 gateway, with owner RLS access verified. The migration refuses an executor different from that anchor. It does not create roles, role memberships, grants on auth.users, or new consent privileges.
- The only proposed gateway signature is `app.b016_company_profile_gateway(uuid,uuid,text,jsonb)` with operations `read` and `save`. The trusted server must derive the actual session and selected live organization from fresh canonical `getSession`, install transaction-local `app.active_org_id` and `app.env` from that context, perform the existing canonical consent and partner checks before and after gateway work, prove transaction health, flush deferred constraints, recheck current authority, and verify the actual COMMIT tag. Those context settings are not an independent identity proof: auth_sessions has no selected-org column. Service access outside this trusted adapter is not a universal seal. No client actor, role or organization field is authority.
- The gateway locks session, relevant flag, organization, admin membership, exact jurisdiction and extension, and rechecks session expiry after waits. Both global `enabled:true` with an all-valid UUID allowlist containing the company and the same company's strict boolean flag must be ON. Missing/malformed flags are OFF. It is not a complete consent/partner policy: the future adapter must enforce those current policies on the same transaction. Existing raw/old writers and the final admission-read-to-COMMIT interval remain outside a universal concurrency guarantee.
- `read` accepts `{}` and returns an admin DTO with name/country/jurisdiction, legal name/identifier, address and `expected_version`. `save` accepts an exact allowlist: `expected_version` plus at least one of `legal_name`, `tax_id`, `address`; address has exactly three string keys. No changed value means unchanged without audit/version inflation; a different stale request returns stale. The opaque digest uses `pg_catalog.sha256(convert_to(...,'UTF8'))` and `encode` over a canonical JSON array containing actual organization xmin text, UTC microsecond updated_at, scoped base values and extension schema/data/version. This improves stale/ABA detection but is not an old-writer fence. Only actually changed base columns are written.
- New/changed legal name is bounded to 200 Unicode code points, identifier to 100, city/district to 100 each and street to 300. Exterior whitespace is trimmed; controls rejected; all-empty clears, and a nonempty city or district requires street. Unchanged legacy base values remain readable. Reviewers and PE must specifically verify the exact fixed Unicode trim set and database locale/control-character behavior against the intended client validator; no parser or runtime validation occurred here.

## Audit and privacy

An address-only change creates a dedicated metadata-only event in the same transaction, containing field names, scope/source/environment and actor metadata, not address/name/identifier values or digest. A base organization update continues to fire the existing `trg_organizations_audit`/`fn_audit`: that generic trigger records full old/new organization rows, including legal name and tax ID. The dedicated event does **not** redact, remove or sanitize that existing record. No generic audit trigger is disabled. No request IP is claimed by this proposal.
