## Narrow review candidate: prevent fresh lease creation on archived ancestry

`src/server/domain.ts:842–845` is the shared staff-only admin/manager `createLease`, called by form adapter `src/server/lease-form.ts:68–70` and flow API `src/app/api/flows/[action]/route.ts:28–30`. Its space lookup `domain.ts:935–952` currently checks the selected room's `r.archived_at` in the room branch and the selected unit's `u.archived_at` in the whole-unit branch. It does **not** check `p.archived_at` in either branch, and the room branch also omits `u.archived_at`. Joins do not explicitly assert each ancestor org despite schema relationships/RLS. Thus source supports a stale/directly submitted selection reaching a currently archived parent; an existing DB trigger `20261018120000_schema.sql:1669–1710` derives the unit/property and checks target mode, currency and overlap, but its shown body does not check archive state. No production incidence or live target catalog is established.

Candidate for separate independent review: on a **fresh** create, resolve the selected room or whole unit with organization-scoped ancestry and require selected room, containing unit and property to be unarchived, preserving correct rental mode. Reject unavailable target with existing generic not-found/error behavior before linking or creating any tenant, lease, signature or related row. Preserve existing `domain.ts:881–925` idempotent/recent-pending return semantics: these return before the fresh lookup; do not break replay or claim a previous successful result is a new lease. Do not alter fee/rent/deposit/signing, flags, rights or unrelated operations.

A predicate alone is a point-in-time read, not full race protection. Review a short in-transaction, org-scoped lock/read of actual property, containing unit and selected room in a deterministic order (`FOR SHARE` only if current role grants and RLS really permit it), re-evaluating `archived_at` and identity after acquiring locks and retaining locks through the fresh create commit. The existing `lease:<roomId>` advisory lock only coordinates participants that use it; no archive writer has been established as taking it. PostgreSQL row locks may serialize a concurrent `UPDATE archived_at` on those same rows, subject to actual permissions, trigger behavior and lock ordering. If an archive commits first, fresh create rejects; if create obtains the locks and commits first, a future archive must independently check resulting active work before committing. This candidate alone does **not** enforce that future archive check, cover raw/direct old lease writers, or guarantee universal archive consistency. Verify exact lock mode/privileges and whether RLS conceals rows in isolated tests; if no safe minimally scoped lock is available, present predicate-only protection with its explicit race limitation for review instead of claiming it solved.

Proposed focused evidence, **NOT RUN**: active whole-unit and by-room positive paths; archived property with otherwise active unit/room, archived unit with active room, archived room, cross-org/unavailable IDs; both form and API caller paths, no new contact/lease/signature on denial, existing identity reused, permission denied, ordinary replay and recent-pending behavior preserved. Two-session tests pause an archive update and a fresh create in both lock orders and test rollback; establish what actually waits and what the later transaction observes. Verify row-lock role/RLS permissions, lock order, unrelated property concurrency and old direct writer limitations. Run only after ownership, exact source review and scope authorization. No new table/migration is assumed for this bounded local application behavior.
