## Existing-schema next capability for review

A useful next increment is an **authorized read-only property/unit/room dependency and history preview**, not yet an archive button: for the exact selected org and actual target, show the target and its ancestry, a bounded list or counts of specifically verified current linked work, and access to already authorized historical lease/file routes where they actually work. Explicitly distinguish unknown/unavailable counts from zero, identify which categories were checked, and do not assert a policy outcome. Reuse current `archived_at`, existing table links and `props.view`/`props.edit` role boundaries (`src/server/perms.ts:11–15`), current org/env/session and existing RLS. Display only fields allowed to that specific staff role; e.g. no accountant contact details just because they may view a property. This read slice can be designed and implemented against existing schema with a separate exact source review and isolated tests; it does not itself enforce archive or guarantee a later write is safe. Existing B015 directory edit feature control covers directory contact edits (`20261031100218_b015_tenant_directory_edit.sql:5–8,50–88`), not general archive authority; any future rollout controls need their own documented design, not an implicit enable here.

A later property/unit/room archive command can potentially use existing timestamps and audit rather than a new table **if** its exact matrix and safety contract are accepted. Derive actor, actual org/environment and target from server context, check active admin/manager relationship and consent/session/feature rules, scope all queries by actual org, and lock actual existing hierarchy in deterministic property → unit → room order, consistent with the proposed fresh-create guard. For property/unit with multiple descendants, obtain rows in deterministic ID order and analyze child insertion/phantom protection; a lock on existing rows alone cannot prevent a new linked lease, ticket, invoice or child from appearing through a writer that does not participate. Re-read target ancestry and relevant sources after locks; abort/return unavailable on drift or insufficient coverage. Set only selected target's `archived_at` and audit reason/actor if and when supported; no deletion, flag activation, forced dependent changes or product-policy assumption. Replay and concurrent archive/restore semantics require explicit review. Old/raw writers and archive-after-create remain unresolved until all relevant operations share a demonstrably effective protocol or narrower DB guard is designed; a successful read and app-side final check do not create universal serialization. Schema/function work is justified only by the concrete safety or durable metadata gap, followed by Codex design and PE target/security/approved non-Mac application—not presumed from this assessment.

## Owner and contact identity boundary

`contacts.archived_at` is a shared contact attribute, not owner-only archive metadata. Current portal selection `src/server/session.ts:185–187` and `auth.ts:193,234` filter archived contacts; RLS helpers `schema.sql:1981–1995` exclude them for several tenant/contact relationships, while property-owner helper `:1997–2002` uses different conditions. A contact can be both owner and tenant (`schema:209–215`), and owner lists filter contact archive (`queries.ts:937,1475`). Setting contact `archived_at` merely to hide an owner therefore can change tenant or owner authentication/history semantics in some paths. Do not toggle `is_owner`, end `property_owners.effective_to`, or delete/recreate a contact to simulate archive: those mutate role or ownership history and have broader effects.

If the desired product behavior is **owner-directory hiding without disabling a shared contact/portal identity**, checked-in contact schema has no independent owner-only archive field; a narrow owner-specific durable state may be needed. Its precise scope (org/contact versus ownership relationship), privilege, audit, restoration, historical and portal access, row lifecycle/reset, old-worker filtering and migration compatibility must be designed and reviewed first. This is a conditional metadata gap supported by current fields, not authorization to add a table/column or change identity behavior. If an entirely different archival semantics is selected, re-evaluate from that explicit decision. No already accepted source justifies an owner-wide portal disable or a blanket new consent policy.
