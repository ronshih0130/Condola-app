## Corrected contract

The migration adds nullable `contacts.owner_archived_at`, `owner_archived_by`, and `owner_archive_reason`. Owner archive never changes `contacts.archived_at`, `is_owner`, tenant/vendor roles, login identity, ownership links/effective dates, statements, files, or financial state. Restore clears only the three owner fields. Existing audit/updated-at triggers remain in effect.

An owner with an assignment to a non-archived property whose `effective_to` is absent or today/later is blocked. Historical links and links to retired properties remain intact and readable. This also makes a new assignment and owner archive mutually exclusive under the contact lock. No automatic detachment, duplicate contact or automatic restore is introduced.

`ArchiveKind` now includes `owner`. Active owner directory/assignment options omit owner-archived contacts only when `record_archive` is ON. The statements page explicitly requests `listOwners(session, true)` so financial/history options retain archived owners. `ownerEditor`, statement/portal entitlements, tenant and vendor predicates retain their existing authority. The existing archive UI supports the owner route and restore; the owner page links to it only under the strict feature conjunction; the archive-list owner wording uses the same gate. Frozen en/zh-TW rendered OFF HTML is compared byte-for-byte. The owner dependency labels are translated in both en and zh-TW.

All new functions explicitly revoke ALL from PUBLIC, anon, authenticated and service_role before granting the required access. Every new SECURITY DEFINER function fixes `search_path=pg_catalog,public,app,pg_temp` with pg_temp last; all relation references are schema-qualified. Only service_role receives gateway EXECUTE. Flag reads and the invoker lock-path helper are executable by API/service roles. The narrow `b015_archive_lock_ticket` definer is also executable by these roles: it authorizes admin/manager/maintenance membership or the caller's exact lease ancestry before and after locking. It only locks/validates; maintenance-ticket INSERT/UPDATE still uses its existing RLS. This preserves tenants and maintenance staff who can submit tickets but cannot UPDATE parent properties. It grants no table mutation or policy changes. Trigger helpers, dependency reads and context validation have no direct application EXECUTE. `anon` receives app schema USAGE solely for the invoker helpers; this grants no table access. Local catalog tests check effective function privileges and the fixed search paths. There are no new private tables, role memberships, broad table grants or seed wipe entries.

The earlier proposal's new dedicated writer role / all-principal seal is deliberately replaced by the requested **actual `current_user` authenticated/anon boundary**. Trusted service_role and existing definers retain their prior authority. The existing server connection may select service_role; an API caller cannot call the gateway merely by setting JWT/session/archive GUCs. The gateway is not a general SQL callback or a public RPC. Application consent/session resolution still occurs at the existing server action boundary. Target connection-role membership, ownership and deployed grants need independent hosted review.

Raw DB admission covers leases, property_owners, units, rooms and maintenance_tickets. Active ticket insertion, reopening and ancestry changes acquire the same property/unit/room locks and reject archived ancestry. A room-only ticket resolves and retains its unit so archive dependency checks cannot miss it. Existing dispatch/signing/utility definers retain their trusted authority and application admission; the former exclusion of API-role maintenance writes has been removed.

## Lock order and concurrency

Physical parent locks are `FOR NO KEY UPDATE`, held through transaction end: **property → unit → room → contact** per path. Property restore locks its retained current owner contacts in UUID order and rejects any archived owner. Unit reparent locks both old/new properties in UUID order with NOWAIT and rejects its own/old ancestry archive plus any dependent room, lease, ticket, meter, expense, listing or utility run, including history. Owner archive only needs its contact. Row triggers do not sort locks across separate rows of an INSERT/UPSERT batch. Parent and target values are re-read after waiting. NO KEY UPDATE conflicts with the other admission/archive lock while remaining compatible with FK key-share checks.

Existing app operations keep their advisory-before-physical-row protocol. Raw admission acquires no advisory lock, so it cannot wait for an app advisory key while holding the physical parent the app needs. INSERT and gateway paths wait in canonical parent order. Raw UPDATE already holds its target tuple before a BEFORE trigger can run; parent acquisition therefore uses NOWAIT, yielding `55P03`. Opposing multi-parent INSERT/UPSERT batches may still deadlock (`40P01`). Both abort the whole transaction; shared DB error mapping returns `errors.busy`, all existing action boundaries retain that key, and archiveCommand returns `busy`. No automatic retry is introduced. Both use existing bilingual `i_portal_timeout` retry copy. PostgreSQL deadlock detection bounds cycles; archiveCommand also retains its five-second lock timeout. No caller-set GUC or trigger-depth bypass is used.

Deterministic two-connection tests cover assignment vs owner archive, lease creation vs unit archive, property restore vs owner archive, maintenance insertion vs archive (both orders), and whole-unit mode changes while lease admission waits. Five guarded tables exercise INSERT ON CONFLICT insert/conflict paths. Opposite-order two-parent INSERT and UPSERT batches establish observed wait edges, require one 40P01 victim, and verify only the winner's full two-row batch remains. The first transaction holds the relevant parent lock; the test waits for a real `pg_blocking_pids` edge before releasing it. Each asserts exactly one successful operation and no archived-parent/active-child state. Separate unit UPDATE and ticket reopening tests exercise NOWAIT; reopening retries after the archive commit reject the archived ancestry. Actual portfolio/lease/ticket action functions (request/IO mocked) verify both SQLSTATEs become localized retry responses and run only once. A temporary-shadow table test checks definer resolution. Runner-owned transaction testing recreates the migration then forces its appended history insert to fail, asserting DDL/probe rollback and preservation of original function OIDs. The original authorization-loss/audit rollback race now observes the gateway SQL instead of the removed direct UPDATE, retaining its original rollback assertions.

The migration contains no file-level BEGIN/COMMIT or SET LOCAL. The runner must own the transaction spanning DDL and its history insert. It adds no independent commit boundary.
