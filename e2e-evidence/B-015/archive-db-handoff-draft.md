## Concrete candidate trusted boundary and fixed transaction flow

Candidate architecture, not an assertion of target state: a private `b015_archive_broker` NOLOGIN/NOINHERIT role has no membership and no EXECUTE by default; the eventual verified dedicated server DB login alone receives membership/EXECUTE under a separately reviewed target binding. The actual server login, pool mode, transaction identity and privilege inheritance are unknown. The gateway checks a non-spoofable `session_user` against an explicitly approved immutable database principal or verifies its separately reviewed membership in the broker role; it fails closed if unbound. No local provisioning of logins, passwords, credentials or keys occurs here. A trusted server connection means callers cannot issue arbitrary SQL through that connection or invoke the gateway using attacker-selected user/session values. Merely passing a UUID or setting a JWT/GUC is not proof. Do not grant broker access to authenticated, service_role, anonymous, PUBLIC or generic client pools. Review whether a transaction-pool/role-switching proxy preserves a distinguishable `session_user`; if it does not, require an equivalent independently authenticated server-only connection or stop. Strong server isolation and PE-verified identity binding are release blockers, not PE product design tasks.

The server resolves its HTTP-only session cookie using the established SHA-256 token lookup in `src/server/session.ts`, and only a verified backend invokes the broker using internally derived session ID, actor ID, selected org, live org and environment; the browser's rendered scope is compared against that fresh result, not trusted as authority. SQL re-reads `public.auth_sessions` by ID and actor, requiring `revoked_at IS NULL` and `expires_at > clock_timestamp()`; it resolves live active `org_members` admin/manager and actual selected/live organization relationship, and checks current consent and partner consent. Current consent is the latest table record ordered by `recorded_at DESC, id DESC` with accepted timestamp and version logic from `consentCoversCurrent`, including its date-baseline semantics; do not replace it with a simplistic equals-current test or invent legal text. The final design must establish how those exact app predicates, partner-consent state, and concurrent new consent/session/member changes are rechecked and serialized through commit. A lock of only the current consent row cannot prevent a later inserted latest row. If all such writers cannot coordinate against a stable shared lock, prove an equivalent serialization or return busy/unknown; do not claim fresh authorization from stale data. Current app readSessionOn has a missing-consent fallback, but archive requires current consent and must fail closed if missing. User/actor parameters and `auth.uid()` alone do not prove cookie possession.

Use distinct fixed-signature gateways, no dynamic identifiers or caller SQL: (1) `b015_archive_observe` returns the same authorized safe projection and exact raw comparison tuple for property/unit/room or owner; (2) `b015_archive_change` accepts closed kind and desired enum, org/target IDs, opaque expected token plus the associated exact server-retained tuple, bounded reason and UUID trace; (3) narrowly scoped admission gateways for actual new/reopened/reparented operations; (4) a fixed mode-conversion operation. The broker does not offer arbitrary table read or a generic update helper. The fixed SECURITY DEFINER writer owns the marker-changing function; no caller is a member of that writer or can SET ROLE to it. Define only narrowly required SELECT/UPDATE privileges and explicit RLS policies for that dedicated owner, once source and actual target privileges are reconciled; the owner is NOBYPASSRLS. Any role-specific read policies must not be granted to app roles and must be paired with strict gateway identity/scope checks. Function search path is explicit with `pg_catalog` first, all relations are fully qualified, functions REVOKE PUBLIC and are granted only to the unbound broker after target binding. If owner or migration-principal privilege changes to existing objects are needed, identify them as a separate pending exception.

Inside a single transaction, the server validates cookie and actual scope, gets the before path; takes agreed ancestry keys in order, then re-reads actual same-org hierarchy after waits, including mode and unit/room parent identity; obtains actual target/business row locks after advisory locks; verifies strict OFF-by-default feature controls and complete dependency coverage; checks fresh authority and the original CAS; writes only the target marker through the fixed definer gateway with the invoker marker guard checking real `current_user`; flushes constraints, repeats authority checks at commit boundary, and directly commits. `changed` may be emitted only after awaited COMMIT; commit uncertainty remains UNKNOWN. Current app token is SHA-256 of `JSON.stringify` of an **ordered SQL row** containing `property_id,unit_id,room_id,mode,property_name,unit_label,room_label,property_archived,unit_archived,room_archived,px,ux,rx,pu,uu,ru`, with `px/ux/rx` tuple xmin text and `pu/uu/ru` timestamp strings preserved at UTC six fractions or NULL. The future design must agree one canonical byte recipe with backend; PostgreSQL `jsonb` rendering cannot be assumed identical to JavaScript JSON serialization. A viable design is that the trusted server hashes and compares the exact ordered row while holding the same transaction and locks, then passes the exact typed observation tuple into the fixed write gateway, which rechecks each stored value under those same locks; otherwise coordinate a single byte recipe and update both sides before freeze. Passing just a caller-supplied claimed hash to a privileged gateway is insufficient. Owner-specific version, identity and ordering are still Codex design work.

The ordinary SQL role cannot atomically take advisory locks before raw UPDATE's tuple lock using a row trigger. Therefore the concrete release strategy is to inventory each old/direct writer and either (a) port it to fixed pre-row-lock gateway plus fence/revoke its direct DML capability, preserving unaffected operations through narrowly scoped gateways/privileges, or (b) demonstrate a different reviewed protocol with equivalent ordering and complete writer fencing. If raw principals retain broad table UPDATE, a marker trigger can prevent marker forgery but cannot guarantee admission for arbitrary operations; report the old/raw guarantee incomplete. This includes direct source writers, imports, scheduled/old workers and any privileged bypass principal. New/activation/reopen/reparent admission must resolve existing same-org parents positively, take the canonical keys, re-read exact ancestry and active state after waiting, and preserve original operation-specific authorization. No user-controlled bypass flag. Existing whole-unit migration archived rooms only in a historical SQL migration; source inventory must determine actual runtime conversion paths before declaring a runtime port equivalent.
