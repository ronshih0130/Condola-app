## Product decision to record

Recommend **base-role ceilings**. A template belongs to a company and one existing base persona. An assigned member retains that persona and can use only a selected subset of its existing permission keys. The assigning Admin must possess every permission granted and current effective administration authority. The four base personas, not a label supplied by the member, continue to govern immutable privacy and specialized domain rules. Allow assignment only to an active member of that same live organization with the matching base persona. An unassigned member retains existing base behavior. Support all four personas subject to owner/recovery guards. Never grant new platform-admin rights from a custom role. A custom template named “Admin” is not a base Admin.

Alternative product policy would permit a base Manager to acquire e.g. an Accountant-only financial action or an Admin-only security action. That requires explicit per-key delegation decisions, privilege limits and an independent redesign of hard-coded role and SQL policies. The canonical sources do not choose this. Ron should decide **restriction-only templates vs cross-base delegation** before authoring effective permission grants or activating a role. A disconnected evaluator can exercise both policy choices, or take the eligible keys as explicit input. Do not hard-code the restriction-only recommendation as product truth before Ron decides. Keep full-org audit, raw identifier/photos/portal rules and billing-owner privileges outside any delegated checkbox. Treat data.export as reserved until its actual operation, audience and enforcement are mapped; do not label the property CSV a full-company export solely by similarity. Decide with Ron only if ambiguity affects which privileges a role can grant. A capability which cannot be mapped to real enforcement must not appear as supported.

| Example assignment | Base ceiling | Delegation within supported keys |
|---|---|---|
| Manager loses messages.send | Allowed | Allowed |
| Manager receives bank.reconcile or pay.reverse from an authorized Admin | Denied by target base | Potentially allowed only if Ron selects these delegable keys, the grantor has them, and the underlying records, actions, raw policies and audit enforce them |
| Accountant receives tickets.update | Denied by target base | Potentially allow ticket operations where expressly supported; photo signing and viewing remain denied regardless |
| Non-Admin receives team.manage or settings.edit | Denied by target base | Requires an explicit governance decision. A delegated UI/settings key must not grant rights to manage roles, full company audit or platform administration by implication |
| Portal person requests any staff entitlement | Denied | Denied; their existing portal-specific rights use a different boundary |

**Question for Ron:** Should a custom role only remove permissions the member’s base role already has, or may a qualified Admin also grant supported permissions outside that base role, such as Manager bank reconciliation? If cross-base delegation is intended, retain actor grant ceiling and mandatory persona denials, and confirm which management/finance permissions are nondelegable before enabling them. Under that choice the effective set is the explicit template set constrained by the approved delegable catalog and immutable restrictions. It is *not* intersected with the old target base matrix for selected delegated keys. Service, RPC and raw RLS implementations that currently gate those actions on a base-role list must specifically admit the verified custom grant. Keep other old base paths from silently widening access. These are real product differences; an attenuation-only release cannot claim delegated expansion complete.

The database already requires a billing owner to be a base Admin and has a uniqueness constraint; setMemberRole rejects demoting that owner. The supplied source does not establish a general institutional recovery account, an always-active billing owner or blanket immunity from suspension. Treat preserving a usable recovery Admin/last-admin guard as a B017 requirement, and any extra owner-specific recovery rights as proposed policy for Ron. Do not invent a superuser or new executive override.

## Persistence and write contract

Prepare an inactive Downloads handoff and companion uniquely named `<timestamp>_b017_custom_roles.proposed.sql`, after checking target history, existing timestamp use and owner reservation. No Mac migration/parser or application registry entry. A minimal durable design needs two private org-scoped tables. Role definitions store org ID, immutable role ID, normalized display name, base persona, a bounded duplicate-free set of known permission keys, revision and audit attribution. A distinct role name is unique within the org under documented normalized comparison; reserve names that misleadingly impersonate built-ins. Assignment rows contain org ID, immutable member reference, role ID and revision, unique per membership. Use composite FK (org_id,user_id) to the existing unique active-or-inactive membership identity and composite FK to the role definition (org_id,role_id). Check active status and exact compatible base in the serialized command; changes to the base cannot resurrect stale assignments. No backfill of existing members. A missing role definition behind an existing assignment or unverifiable readiness denies; it never means unassigned. Do not allow delete/cascade of a role with assignments to restore broader base access. Explicit unassignment requires the same privilege checks on the *resulting* base permission set. Define archive or deletion only after all references are separately and knowingly resolved.

Use the existing audit store with one metadata event per committed change and the same transaction/client; identify actor, organization, role/member IDs, previous/new revision and changed permission keys. Do not include free-text profile or contact values. Use B003 ownership/ACL pattern as an anchor, with target catalog proof. RLS-enabled private objects, no blanket table grants or publicly executable authorization/mutation functions. A fixed service-only admin command gateway may perform create, edit, assign, replace/remove and retire. A narrow read/permission predicate may serve authenticated policy evaluation without returning other members' rows; bind actor to real auth.uid/effective membership and selected live org. A service-only call must derive actor from freshly validated session, never accept actor/role as authority from form data. Verify trusted owner, SECURITY DEFINER search path, no public execution, actual owner access and service/grant boundaries. Do not treat request GUCs or service-role access as an independent credential. Avoid FOR SHARE/UPDATE assumptions on tables where deployed grants have not been established.

Serialize on the selected live organization before locking mutable actor/target/template state in a consistent order. Check live/selected org, actual current admin membership and effective team.manage, managed-mode flag, actor grant ceiling, consent/partner and session health after waits. Revalidate expected template/member revision, exact target membership and number of active effective administrators. Require at least one active Admin with effective role-administration ability. Preserve the existing billing-owner/base-Admin constraint; additional recovery protection requires explicit policy. Disallow own role reduction, indirect loss via editing a template assigned to the actor, self-assignment to expand permissions, attempted grant beyond the actor, foreign references, inactive users and last-admin removal. Reject changes that would leave active admins unable to recover the org. A template edit is a bulk privilege change; evaluate impacted assignees under the same lock. Return bounded invalid/forbidden/stale results; a failed mutation, audit or commit rolls all changes back. Replayed exact successful intent must not duplicate versions or audit; resolve lost responses by canonical readback without blind retries.

The existing setMemberRole and deactivate path check last admin using a query separate from UPDATE/audit; reactivation takes a seat org lock. Base role/status, accepted invitations (including updates to an existing membership), deletion and sandbox copying must participate in the same invariant. The original members_admin RLS and public authenticated DML grants permit a raw role/status write in source. A TS-only check cannot guard that route. Close using the narrowest verified policy/privilege/guard change on org_members and legacy writers; prove privileged bootstrap, invitations, seats, billing owner and old paths still work. Prevent bypass by changing the base role, deleting an assignment, or suspending the last recovery admin. Keep fixture/reset/bootstrap distinct from privileged live operations.

## Permission enforcement and rollout

A fresh effective-permission function combines the actual canonical membership, assignment and bounded template keys for the selected company. Use it in navigation/route admission, server actions, direct APIs, file-signing/byte delivery and same-transaction mutation services. Never authorize irreversible operations exclusively from cached UI/session flags. Scope sandbox via its canonical live parent if product permits preview; no sandbox role administration or mutation of live grants. Preserve owner/tenant/vendor lookups and staff base role for privacy. Portal access remains limited to records/files already authorized for that portal; a staff template cannot widen it. Every signed-URL endpoint must reauthorize at issuance and, where an existing proxy serves bytes, at byte access. Already issued, independently valid links need documented expiry/revocation semantics.

Existing app.is_member and app.has_role helpers and many permissive RLS policies are base-role based, and some services bypass RLS. Do not globally redefine app.has_role by mapping role arrays to an invented permission. An array shared by two different operations does not identify the intended permission. Establish a per-operation, per-table/verb enforcement manifest for all eighteen keys and all reachable paths. Add properly scoped restrictive SQL policies or adjust the actual domain RPC/gateway where coarse permissive reads/writes would otherwise bypass an assignment. Multiple permissive policies OR together, so adding another permissive policy cannot narrow access. Owner-executed functions and trusted service writes need their own current admission. Keep legacy read permissions compatible for unassigned users, reconcile multi-key operations explicitly, and audit old-client/raw bypasses. If a key cannot be enforced end to end on the target, park its checkbox and record remaining feature coverage; this is not full B017 acceptance.

Map dashboards, property/unit/room and lease read/edit, tenant contact disclosure, payment record/reverse, reconciliation, statement read/generate/PDF, expenses and period close, tickets and photos, messages, report and broad data export, team and settings. Keep restricted capabilities from becoming privileges via another route (e.g. expense creation on a ticket, finance exports, service signing). Accountant ticket-photo denial must stand even if a broad key is granted. Preserve allowed finance records. Full company audit remains available only to a base Admin within the org; if the custom profile narrows administrative access, it cannot widen the audience. Explicitly preserve historical portal-specific rights and prevent Accountant ID-document disclosure. Use direct row/RPC/file probes for the authenticated actor, not only screenshots of absent controls.

CUSTOM_ROLES is a proposed capability. Register only after reservation, with strict global enabled/allowlisted-org and org opt-in, absent/malformed = management OFF. A switch or missing schema must never broaden a previously restricted member. No assignments means base behavior is identical on the approved old schema. With assignments present, either continue enforcing existing restrictions while disabling management or deny affected access until readiness recovers. Never roll back to a base-only client against active assignments. Prove the old app against new additive objects with no assignments/activation; require a separately verified deny/compatibility bridge or controlled quarantine before any rollback after assignments exist. Test reset, migration collision, old support state, restore and audit privacy. PE must verify actual grants/history/FORCE or owner RLS behavior, backup/restore, exact PostgreSQL target and legacy compatibility on an authorized non-Mac target. Proposed SQL is design text only, unparsed, unapplied and not apply-ready.
