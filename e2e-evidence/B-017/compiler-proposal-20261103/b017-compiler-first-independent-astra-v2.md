# B017 compiler-first proposal v2, independent source review

**SOURCE_GO for the limited PE compiler proposal.** All four v1 blockers are addressed in the frozen source. PE can use this package to review a future, separately authorized disposable compiler target. No target has been verified and no compilation, installation or removal has been demonstrated.

| Previous blocker | Source disposition |
|---|---|
| Routine-body checking | Every entrypoint begins a transaction and includes guard.sql. The guard sets check_function_bodies on and verifies the actual setting before the three pinned input files can be read. This enforces the validation PostgreSQL provides at creation time. Deferred branches remain among the unrun proofs. |
| Socket and peer identity | Before each psql invocation, check_endpoint validates canonical socket/data directory ancestors, ownership and write permissions, the private socket directory and actual socket owner. The invoking, database and server OS identities must agree. The client sets PGREQUIREPEER. The single direct local peer rule must match the approved HBA bytes. The SQL guard also requires the physical HBA path and authenticated system_user equal to peer plus the operator identity, as well as the original cluster, database, single-login and isolation checks. PE must independently establish that this HBA was loaded and that the host, listeners and external workers meet the documented isolation conditions throughout. |
| Recovery provenance | recover-down derives both state hashes from the separately approved original install.json. It requires a successful cycle/install, the same manifest and target, run identity and physical cluster/PGDATA/database. It verifies the linked successful same-run baseline receipt, the four original raw log digests and the exact one/two snapshot markers. The install’s first marker must equal the approved baseline and its second must differ. Stage logs, receipt files and containing directory are fsynced. Fresh database readback must still match the original seal before removal, and both in-transaction and reconnected readback must match the baseline afterwards. A missing original successful install receipt or uncertain commit leaves the target quarantined. |
| FK effects on public tables | The install captures the original trigger catalog on organizations and org_members. parent-fk-delta.sql matches all three specified private-child FKs by ordered columns, referenced parent, ordinary parent type, validation, deferrability and action semantics. It permits only the six extra internal enabled AFTER ROW NO ACTION update/delete triggers linked to the matched constraints. Removing these six new OIDs from the installed snapshot must reproduce the original parent trigger inventory, including full-row/definition fingerprints and enabled state. The normal sealed and restored snapshot checks include this catalog. No authored public business trigger is present. |

All 25 manifest entries and four referenced plan digests matched. The three compiler inputs, four excluded proof drafts, seal, guarded RESTRICT removal and global-role dependency safeguards are byte-identical to v1. The persistent flock still spans the normal cycle on the actual approved PGDATA. I read the source, checked the operator's Python syntax with the standard-library AST reader and checked the installed PostgreSQL 16 reference for system_user, requirepeer and the two RI function names. I did not import the operator, invoke a SQL parser, connect to a database or exercise Linux filesystem/authentication behavior.

**Disposition remains NOT_APPLY_READY.** A future PE target approval must bind the exact package and completed configuration, isolated physical cluster, protected host and sole maintenance operator. F01–F10 remain NOT_RUN. The four proof drafts are excluded from the operator workflow. A shared cluster, app connection, staging, governance activation and feature acceptance are outside this review.
