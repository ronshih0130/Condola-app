This is a complete *scoped foundation handoff*, once its wrapper, seal, rollback and proof harness are authored and independently accepted. It is not complete B017, not the complete 47-operation handoff, and not enrollment ready. B017 stays in progress. No new Ron product-policy decision is required.

The accepted fragments cannot be concatenated and called apply ready unchanged. Their existing service-only EXECUTE grants are future activation points, their own status files say never deploy separately, and their reviews approve only source fragments. The new composition must override those grants in the same transaction, expose no runtime interface, and keep all four private tables empty. This report defines that composition; it does not author SQL or authorize parsing/application on the Mac.

## Seal and install transaction

1. Use a maintenance/migration principal separate from every application connection identity. Before DDL, record the nonsecret target database/environment identity, baseline and package hashes, PostgreSQL version/UTF8/normalization/collation support, schemas/types/FKs and source columns. Verify exact auth/member/org/audit/platform dependencies and applicable policies. Reject any preexisting B017 named role/table/function/policy, unexpected overload or conflicting object; do not adopt it with `IF NOT EXISTS` or replace it. This is a single-use versioned migration. Repeat installation must fail safely, not silently merge an unknown schema.
2. Prove the migration principal can create the two exact role attributes and transfer table/function ownership. PostgreSQL ownership transfer also needs the target owner to have required CREATE privilege in the schema and the migration principal to be able to SET ROLE as required by that target version. Any temporary schema CREATE or owner membership/admin option is narrowly held by the separate migration principal, removed before COMMIT and verified absent for runtime principals. The authority owner retains only required USAGE/source grants; domain owner has no new application access. Abort on insufficient privilege; no broad owner reuse or fallback to runtime ownership.
3. One transaction with error-stop, bounded lock and statement timeouts executes the three pinned inputs in order, followed by the seal. No business rows, organization state, draft role, receipt or assignment are seeded. No custom_roles platform row or organization feature flag is inserted/updated, no role is activated, and no app call or navigation adapter is installed. The installed foundation has zero rows in each private table.
4. Explicitly revoke every privilege on the four private tables (including column privileges and any sequence privilege if target identity differs) from PUBLIC, anon, authenticated, service_role and the exact actual runtime login/group inventory. Do not rely only on RLS: service_role BYPASSRLS still needs ACL permission, while an owner/superuser may invalidate the intended boundary. Expected ACL is authority owner only; unexpected default-grantee access must make the transaction fail until the narrowly scoped wrapper is revised. No global schema-wide revoke is justified.
5. Revoke runtime EXECUTE on **all ten new function signatures**, including the resolver, create and edit endpoints. This explicitly supersedes the three terminal service_role grants in the accepted fragments. Owner execution of its own fixed functions remains available to controlled non-app compiler fixtures. No permanent test grant, test role with runtime membership, public RPC allowlist entry or service bypass is introduced. Fully enumerate actual signatures; no arbitrary-function dispatcher. This makes later flag changes alone incapable of opening the foundation.
6. Before COMMIT assert exact object ownership, function attributes/search paths, ENABLE+FORCE RLS and all fourteen policies; no PUBLIC or runtime direct/column grants, no runtime EXECUTE or inherited owner/SET ROLE path, no unexpected source-table privilege or audit-read grant, no new public triggers/views/RPCs and no flag/data changes. Remove temporary installation privileges. Compare the catalog delta to the manifest; fail the transaction on any deviation. Keep existing public function ACLs/default privileges unchanged. Existing default-privilege migrations do not prove the new app-schema ACLs; inspect effective privileges explicitly.
7. COMMIT only the sealed empty foundation, then verify denial through separate real runtime connections and exact restoration. Transactional DDL prevents a committed grant window; merely putting several files in a folder does not. Dump/restore must preserve final ACLs, not replay an intermediate fragment grant after the seal. A template is sealed only after post-restore negative proof.

**Explicit normal-worker guard:** there is no installed API that inserts prepared/enforced state, assignments or tombstones. Runtime has neither private-table privileges nor an owner-role path nor EXECUTE on a definer that could write them. The create/edit bodies only become usable inside separate privileged disposable test fixtures, and cannot prepare/enroll/assign even there. A guessed SID or GUC, or mistakenly enabled control, does not change the sealed ACL. Assignment/enrollment has no corresponding callable object in this package. Empty state is a checked invariant, not an enrollment permission.

A runtime login with superuser, ownership/assumable authority owner, role-administration escalation or equivalent broad privileged access cannot meet that claim. `db.ts` opens DATABASE_URL before it selects authenticated/service_role, so testing only those final role names is insufficient: check the actual connection login and its inheritance/reset/SET ROLE paths. If that target separation is unavailable, PE can still obtain compiler feedback in a network-isolated disposable clone with no worker connections and a separate test principal. Do not call an app-connected database safely installed until the real login proof passes. This foundation does not quietly rotate worker credentials or bypass the later 03 credential lifecycle work.

## Existing application compatibility and rollback

No current app route calls these new functions; leave application source, permissions, flags and queries byte-identical. Native permissions, real cookie handling, consent/partner policy, portal isolation and existing financial behavior remain the current app contract. The new private owner receives narrowly scoped read/lock/audit policy access; runtime roles receive none. Check that existing roles do not inherit the owner and that source UPDATE grants used for row locks cannot actually mutate source rows through some other applicable permissive policy. A `WITH CHECK(false)` permissive policy is not an overriding deny if another applicable policy allows the write. Target proof must cover this rather than claiming the new policy forces denial universally.

Owner fixtures may insert prepared state and test create/edit only in an isolated child clone/rollback transaction as the maintenance operator, using owner-context calls. Manual auth pins establish test inputs, not real cookie authorization. No app login is granted the functions for positive testing, and no prepared/enforced/assignment fixture is left in the install or template. Actual B017 cookie/consent/partner/write serialization admission remains Codex work with its later adapters. Current native member/invite/reset paths remain unaffected because no authority row or public trigger is installed; representative old-code proof must verify this.

Before COMMIT an installation failure rolls back the entire package, including newly created roles/grants/policies. After a clean sealed installation, the preferred operational rollback is to leave inert objects installed; there is no app feature to disable. If removal is required on an isolated target, the paired down migration first verifies exact package identity, all four tables empty, no later-stage dependencies or runtime connections using them and no additional owner objects/memberships. It removes only the ten new functions in dependency order, four private tables in FK order, the ten new public policies, the exact source-column grants to the two new owners and the now-unused two roles. Drop private policies with their tables. Use RESTRICT and fail on unexpected dependencies; never CASCADE, blanket DROP OWNED or delete historical data. Original public ACLs/policies must match the preflight baseline. If any org has later prepared/enforced state or assignments, this down migration is prohibited; later sticky-enforcement recovery governs that case. Full B017 OFF/rollback after enrollment is not solved by this package.
