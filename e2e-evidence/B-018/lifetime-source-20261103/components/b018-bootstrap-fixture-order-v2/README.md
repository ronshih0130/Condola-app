After those file/path checks, `await createFixture(options).prepare()` makes an exclusive fsynced `contact-order-attempt.json`, then begins one serializable transaction. It locks the exact two unarchived tenant-only user-005 contacts in the two live organizations; no active staff and an exact timestamp tie are allowed. It fingerprints the full catalog and all public/app/auth physical table rows, using typed `record_send` for all untouched contacts and a typed ordered record projection excluding only the target contact's created_at and updated_at. Before commit, the component repeats the comprehensive snapshot inside the transaction and verifies the expected timestamp ordering, unchanged rows and relations, unchanged controls, retained old audits and exactly one matching normal contact update audit; then it rechecks client count, source/receipt lineage and baseline sentinels. Any mismatch aborts the transaction. Commit uncertainty or other failure is QUARANTINE, never auto-retry or blind reversal.

The writer connection closes. An independent fresh read-only connection and repeatable-read transaction then repeat the endpoint/generation, exclusivity, controls, full table/contact and audit comparisons. The prepared receipt contains only metadata IDs and keyed commitments, not contact fields or raw audit data. `contact-order-prepared.json` is exclusively written and fsynced only after successful fresh readback. It is a local fixture receipt, not a feature verdict. The parent must verify its actual child exit, process drain and receipt hash and preserve the audit delta as part of the subsequent baseline.

The parent must serialize this child against baseline creation, wait for verified successful child exit and readback, then exclusively fsync `baseline-started.json` before invoking or importing baseline capture. Checks alone cannot prove absence of a racing actor between filesystem operations; the shared parent stage/ownership and serial execution are required. A sentinel during the fixture or an unknown commit/readback outcome is quarantine. No automatic resume is provided after the durable attempt, even if the process dies before mutation.

Tests are pure in-memory validation over synthetic rows and do not open a database. They do not prove PostgreSQL syntax, driver resolution, actual trigger behavior, catalog/record_send coverage, file race exclusion or parent cleanup. Highest independent source review and a fresh parent lock plus explicit root authorization are required before a single actual fixture invocation.
